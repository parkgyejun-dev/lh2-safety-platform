# KRDS 구현 강제 정책

> 이 문서는 권고사항이 아니라 **필수 개발 규칙**이다.  
> 아래 규칙을 위반한 화면·컴포넌트·Pull Request는 완료로 보지 않으며 병합하지 않는다.

## 1. 기본 원칙

이 프로젝트의 사용자 조작 UI는 **KRDS HTML Component Kit v1.1.0**을 기준으로 구현한다.

KRDS에 공식 컴포넌트가 존재하면 해당 컴포넌트의 **공식 마크업 구조, 클래스명, 상태표현, 접근성 구조를 그대로 사용**한다.

다음과 같은 이유로 공식 컴포넌트를 임의 재구현해서는 안 된다.

- 더 예뻐 보이게 하려고
- 토스·카카오페이와 비슷하게 보이게 하려고
- React에서 구현하기 편해서
- CSS를 줄이기 위해
- 기존 개발자가 만든 컴포넌트가 있어서
- 공식 컴포넌트가 복잡해 보여서

## 2. 반드시 KRDS 공식 컴포넌트를 사용할 항목

KRDS에 해당 컴포넌트가 있는 경우 사용자 정의 컴포넌트로 대체하지 않는다.

- Header
- Main Menu
- Breadcrumb
- Button
- Badge
- Text Input
- Select
- Radio Button
- Checkbox
- Textarea
- Step Indicator
- Structured List
- Structured List Table
- Table
- Tab
- Modal
- Accordion
- Disclosure
- Contextual Help
- Help Panel
- Critical Alerts
- Footer
- Identifier
- 기타 KRDS v1.1.0에 포함된 조작형 UI

예:

- 금지: `<button className="custom-primary-button">`
- 사용: `<button className="krds-btn primary">`

- 금지: 사용자 정의 카드 목록으로 평가모듈 목록 구현
- 사용: KRDS `krds-structured-list` 우선 검토

- 금지: 임의 단계 표시기
- 사용: KRDS `krds-step-wrap`

## 3. 사용자 정의 CSS 허용 범위

사용자 정의 CSS는 다음 목적에 한해 최소한으로 사용한다.

- 화면 전체 배치
- 섹션 간격
- 최대 폭
- 반응형 배치
- 공학 그래프·지도 영역의 크기
- KRDS에서 제공하지 않는 도메인 전용 시각화 컨테이너

다음은 금지한다.

- KRDS 버튼의 색상·모서리·높이를 임의 변경
- KRDS 입력창의 테두리·상태표현을 임의 변경
- KRDS 배지를 비슷한 모양의 자체 배지로 대체
- KRDS Step Indicator를 별도 스타일로 재제작
- KRDS Header/Footer를 닮은 자체 Header/Footer 제작
- 컴포넌트 외형을 토스·카카오페이식으로 강제로 덮어쓰기

## 4. 토스·카카오페이식 UX를 적용하는 방법

토스·카카오페이의 **브랜드 디자인을 모방하지 않는다.**

다음 UX 원칙만 차용한다.

- 한 화면에 한 가지 핵심 작업
- 첫 화면의 정보량 최소화
- 핵심 결과를 먼저 제시
- 필요한 정보만 단계적으로 공개
- 짧고 자연스러운 한국어
- 입력 반복 최소화
- 넓은 여백과 명확한 정보 위계
- 사용자가 다음 행동을 바로 알 수 있는 구조

즉 **컴포넌트는 KRDS**, **정보구조와 흐름은 간결한 금융앱 수준**으로 설계한다.

## 5. 예외: 과학·공학 시각화

다음 항목은 KRDS에 전용 컴포넌트가 없으므로 예외를 허용한다.

- F-N 곡선
- 개인적 위험도 등위선
- 사고빈도 곡선
- 제트화재 거리-복사열 곡선
- 누출유량 시간곡선
- 민감도·불확실성 그래프
- GIS 지도
- 영향범위 및 위험도 Overlay

이 경우 Plotly.js, MapLibre GL JS, deck.gl 등 전용 시각화 도구를 사용할 수 있다.

단, 다음은 반드시 지킨다.

- 그래프 주변 버튼·탭·필터·입력은 KRDS 사용
- 범례·축·단위는 공식 용어 사용
- 색상만으로 상태를 구분하지 않음
- 동일 결과를 표 형태로도 확인 가능하게 함
- 시각화 라이브러리의 기본 툴바는 필요 최소한만 노출

## 6. 문장 및 용어 강제 규칙

### 6.1 공식 용어

기술용어, 설비명, 기준명, 사고현상명은 공식 명칭을 우선한다.

임의 축약, 의역, 신규 용어 생성을 금지한다.

예:
- 사건수분석(Event Tree Analysis, ETA)
- 사고영향평가
- 방호설비 신뢰도
- 개인적 위험도
- 사회적 위험도
- 보호시설과의 안전거리

### 6.2 번역투 금지

다음 표현은 화면 문구에서 원칙적으로 사용하지 않는다.

- ~에 대해 수행합니다
- ~을 통해 가능합니다
- ~관점에서
- ~를 기반으로
- ~에 대한 평가를 수행합니다
- 본 화면에서는 ~할 수 있습니다

자연스러운 한국어로 바꾼다.

예:
- "설비에 대한 정보를 입력합니다" → "설비 정보를 입력하세요."
- "리스크 기반 평가를 수행합니다" → "리스크를 계산합니다."
- "결과에 대한 상세 정보를 확인합니다" → "상세 결과를 확인합니다."

## 7. 신규 화면 개발 절차

새 화면을 만들기 전에 반드시 다음 순서로 검토한다.

1. KRDS v1.1.0 공식 저장소에서 해당 컴포넌트 존재 여부 확인
2. 공식 마크업 확인
3. 공식 컴포넌트로 화면 구성
4. 필요한 경우에만 배치용 CSS 추가
5. 공식 용어와 자연스러운 한국어 검토
6. 데스크톱·모바일 확인
7. 시각 검수
8. Pull Request 체크리스트 확인

## 8. 금지 예시

다음 코드는 프로젝트에서 원칙적으로 허용하지 않는다.

```tsx
<div className="custom-card">
  <button className="custom-blue-button">분석 시작</button>
</div>
```

KRDS 컴포넌트가 존재한다면 다음 방향으로 구현한다.

```tsx
<button type="button" className="krds-btn primary">
  분석 시작
</button>
```

## 9. 완료 기준

아래 중 하나라도 충족하지 못하면 해당 화면은 완료가 아니다.

- KRDS 공식 컴포넌트 우선사용 확인
- 자체 UI 재구현 여부 확인
- 사용자 정의 CSS 최소화
- 공식 용어 확인
- 번역투 제거
- 접근성 구조 확인
- 모바일 화면 확인
- 시각 검수 완료

## 10. 위반 처리

기존 코드에서 이 정책을 위반한 요소를 발견하면 새 기능을 추가하기 전에 우선 교체한다.

특히 다음 기존 사용자 정의 요소는 KRDS 공식 컴포넌트로 교체 대상이다.

- 사용자 정의 Header
- 사용자 정의 평가모듈 목록
- 사용자 정의 Footer
- KRDS에 대응 컴포넌트가 있는 사용자 정의 상태표시
- KRDS 컴포넌트와 중복되는 사용자 정의 입력 UI

이 정책은 보호시설 안전거리뿐 아니라 추후 연결되는 사업소간 경계거리, PSD 분출용량, BOG 처리량, 검사주기 모듈에도 동일하게 적용한다.
