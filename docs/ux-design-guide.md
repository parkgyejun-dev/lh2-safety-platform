# UX·UI 및 문장 작성 원칙

> **필수 규칙**  
> 본 문서는 권고안이 아니다. 모든 프론트엔드 개발은 [KRDS 구현 강제 정책](./krds-implementation-policy.md)을 우선 적용한다.  
> KRDS v1.1.0에 공식 컴포넌트가 있으면 사용자 정의 UI로 다시 만들지 않는다. 이 원칙을 위반한 화면은 완료로 보지 않는다.

## 1. 목표

본 시스템은 공공·기술 시스템의 정확성을 유지하면서도, 사용자가 복잡한 위험평가 절차를 부담 없이 따라갈 수 있도록 설계한다.

화면 경험은 카카오페이·토스와 같이 **정보 위계를 단순하게 정리하고, 필요한 시점에 필요한 정보만 보여주는 방식**을 지향한다. 특정 서비스의 색상·브랜드·화면을 모방하지 않으며, 실제 UI 구성은 KRDS HTML Component Kit v1.1.0을 기준으로 한다.

## 2. 핵심 UX 원칙

### 2.1 한 화면에 한 가지 핵심 목적

한 화면에서 입력, 계산, 결과 해석을 동시에 요구하지 않는다.

예:
- 설비 입력
- 누출 시나리오 확인
- 분석 실행
- 결과 확인

각 단계는 사용자가 지금 해야 할 일을 바로 알 수 있도록 분리한다.

### 2.2 핵심 결과를 먼저 제시

결과 화면에서는 계산식이나 상세 표보다 먼저 다음을 보여준다.

- 규범론적 안전거리
- 리스크 기반 안전거리
- 개인적·사회적 위험도 반영 결과
- 지배 시나리오
- 적용 기준

상세 계산근거는 사용자가 필요할 때 펼쳐서 확인한다.

### 2.3 점진적 정보 제공

전문가용 상세정보를 기본 화면에 모두 노출하지 않는다.

기본 화면:
- 주요 입력값
- 분석상태
- 핵심 결과
- 주요 경고

상세 화면:
- 누출빈도
- 사건수분석
- 방호설비 신뢰도
- 사고영향평가
- 개인적 위험도
- 사회적 위험도
- 민감도·불확실성

### 2.4 표보다 판단 구조를 우선

표가 필요한 경우에도 수치만 나열하지 않는다.

예:
- 현재 설계거리
- 요구거리
- 차이
- 지배조건
- 판정근거

사용자가 '왜 이 값이 나왔는지'를 따라갈 수 있게 구성한다.

### 2.5 입력 반복 최소화

사업소, 설비, 운전조건, 방호설비 등 공통정보는 한 번만 입력하고 여러 분석에서 재사용한다.

## 3. 시각 설계 원칙

- KRDS v1.1.0 컴포넌트만 사용자 조작 UI에 사용
- 넓은 여백과 명확한 정보 위계
- 화면마다 대표 동작은 1개를 우선
- 과도한 테두리와 격자 사용 금지
- 카드 사용은 정보 묶음이 명확할 때만 적용
- 상태·경고·오류는 색상만으로 구분하지 않음
- 숫자는 단위와 함께 표시
- 위험도 값은 과학적 표기법과 의미를 함께 제공
- 복잡한 표는 요약 결과와 상세표를 분리
- 모바일·태블릿·데스크톱에서 동일한 정보 구조 유지

## 4. 기술 시각화 원칙

과학·공학 시각화는 KRDS 조작 UI 안에서 콘텐츠로 제공한다.

- F-N 곡선
- 개인적 위험도 등위선
- 사고빈도 곡선
- 제트화재 거리-복사열 곡선
- 누출유량 시간곡선
- 민감도 및 불확실성 결과

그래프 자체는 Plotly.js, MapLibre GL JS, deck.gl 등 전용 렌더러를 사용할 수 있으나 다음을 지킨다.

- 툴바·버튼은 공통 UX와 충돌하지 않도록 최소화
- 범례와 축 이름은 공식 용어 사용
- 색상만으로 등급을 구분하지 않음
- 기준값은 그래프 안에서 직접 확인 가능하게 표시
- 그래프와 같은 결과를 표 형태로도 확인 가능하게 제공

## 5. 문장 작성 원칙

### 5.1 번역투 금지

다음과 같은 표현을 피한다.

- ~를 기반으로
- ~에 대해 수행한다
- ~을 통해 가능하다
- ~관점에서
- ~에 대한 평가를 수행한다

문맥에 따라 자연스러운 한국어로 바꾼다.

예:
- '리스크 기반 평가를 수행합니다' → '리스크를 계산합니다'
- '설비에 대한 정보를 입력합니다' → '설비 정보를 입력합니다'
- '결과에 대한 상세 정보를 확인합니다' → '상세 결과를 확인합니다'

### 5.2 공식 용어 우선

기술용어, 기준명, 설비명, 사고현상명은 임의로 줄이거나 새로 만들지 않는다.

예:
- 사건수분석(Event Tree Analysis, ETA)
- 개인적 위험도
- 사회적 위험도
- 사고영향평가
- 방호설비 신뢰도
- 보호시설과의 안전거리

공식 기준에서 사용하는 명칭이 확인된 경우 해당 명칭을 우선한다.

### 5.3 짧고 자연스러운 문장

화면 문구는 설명문보다 사용자의 행동과 결과를 중심으로 쓴다.

좋은 예:
- 사업소 정보를 입력하세요.
- 분석할 설비를 선택하세요.
- 계산이 완료되었습니다.
- 지배 시나리오를 확인하세요.
- 상세 계산근거를 확인할 수 있습니다.

피할 예:
- 본 화면에서는 사업소와 관련된 기본적인 정보를 입력할 수 있습니다.
- 사용자는 분석 수행을 위한 대상 설비를 선택할 수 있습니다.

### 5.4 한 문장에 한 가지 의미

문장 하나에 조건, 예외, 설명을 모두 넣지 않는다.
필요하면 문장을 나누거나 도움말로 분리한다.

## 6. 결과 화면 문장 예시

### 권장

**보호시설과의 안전거리**

- 규범론적 안전거리: 00 m
- 리스크 기반 안전거리: 00 m
- 개인적·사회적 위험도 반영 결과: 00 m
- 지배 시나리오: 24 in 하역배관 10% 누출, 지연점화
- 적용 기준: EIGA Doc 75/21

### 지양

'상기 결과는 다양한 위험인자를 종합적으로 고려하여 산출된 최종 안전거리 결과입니다.'

## 7. 미구현 모듈 표시

다음 모듈은 현재 계산기능을 제공하지 않는다.

- 사업소간 경계거리
- PSD 분출용량
- BOG 처리량
- 검사주기

화면에는 단순히 '미구현' 상태를 표시하고, 임시 계산식이나 추정값을 제공하지 않는다.

## 8. 개발 시 확인사항

새 화면을 추가할 때 다음을 확인한다.

1. 이 화면에서 사용자가 해야 할 일이 하나로 명확한가
2. 첫 화면에서 꼭 필요한 정보만 보이는가
3. 공식 용어를 사용했는가
4. 번역투가 없는가
5. 같은 정보를 반복 입력하게 하지 않았는가
6. 결과의 근거를 추적할 수 있는가
7. KRDS v1.1.0 컴포넌트로 구현 가능한가
